# Три задачи по базе продаж (Cursor Cloud Agents)

Каждая задача — отдельный Cursor Cloud Agent, изолированная ветка
`cursor/<slug>`, PR в `sakura565-afk/openclaw-cursor`.

**База для всех трёх:** пакет `furniture_sales_database/sales_tools/`
(`importer.py`, `analyzer.py`, `README.md`) + обезличенная фикстура
`furniture_sales_database/sales_tools/fixtures/sales_sample.db`.
Схема таблиц и правила — в `sales_tools/README.md`.

**Общие требования к каждой задаче:**

- Только `pytest`-тесты, без сети, без доступа к реальным данным.
- Тесты работают на `furniture_sales_database/sales_tools/fixtures/sales_sample.db` (или на временной БД,
  собранной в `tmp_path`).
- Никаких реальных имён контрагентов/салонов/менеджеров в коде, тестах и
  фикстурах.
- Никаких абсолютных путей к `C:\Users\user\...` — путь к БД через аргумент
  или относительный.
- Только stdlib + `pytest` (+ `openpyxl` для парсера xlsx, он уже в
  окружении).
- Коммит-сообщение в стиле репозитория: `feat(...): ...` / `fix(...): ...`.
- В описании PR — что изменилось, как проверить, какие цифры изменились.

## Задача 1 — `cursor/sales-import-hardening`

**Заголовок:** `feat(sales): устойчивый импорт срезов 1С — идемпотентность, покрытие, реестр`

**Суть.** Сейчас `importer.py` при каждом запуске удаляет срез месяца и
вставляет заново. Это работает, но:

1. **Нет реестра срезов.** В таблице `imports` лежит одна строка на файл, но
   непонятно, какой срез ЗАМЕНЯЕТ какой. При импорте старого файла поверх
   нового можно потерять данные. Нужна таблица `slices` (или поля в
   `imports`), где для каждого среза хранится: `source_file`, `period`,
   `month`, `report_filter`, `rows`, `qty`, `amount`, `imported_at`,
   `supersedes` (какой срез заменил), `is_current`.
2. **Нет защиты от регресса покрытия.** Проверка «новый срез покрывает все
   контрагенты старого» есть, но она сравнивает только *наличие* контрагента.
   Нужно проверять, что по каждому общему контрагенту qty/amount нового среза
   **не меньше** старого (накопительный срез может только расти), и падать с
   внятным сообщением, если это не так.
3. **Нет проверки «Итог» на уровне контрагента.** Сейчас сверка с суммой листьев
   есть, поконтрагентная — в dry-run, но при `--apply` ошибка поконтрагентного
   расхождения не останавливает импорт (сверка идёт по `leaves`, а
   `buyer_rollups` из файла не сверяется с разбором в БД).
4. **Нет транзакционной целостности.** Удаление старого среза и вставка нового
   идут отдельными `execute`, без единой транзакции — при сбое на середине
   месяц остаётся без данных. Нужна одна транзакция с `BEGIN IMMEDIATE`.

**Что сделать:**

- Добавить таблицу реестра срезов и её миграцию (идемпотентно, для существующих
  БД).
- Сделать импорт транзакционным: при любой ошибке откат, месяц не теряется.
- Добавить поконтрагентную проверку «новый ≥ старый по qty и amount» с
  понятным сообщением, какие именно контрагенты регрессировали.
- Сделать сверку с rollup-строками контрагентов из файла обязательной при
  `--apply` (сейчас она только печатается).
- Покрыть всё тестами на `tmp_path`-базе: регрессия покрытия откатывается,
  транзакция откатывается при ошибке, повторный импорт того же файла
  идемпотентен (та же сумма, не задвоение).

**Критерии проверки:**

```bash
python -m pytest tests/test_sales_importer.py -q
```

- Повторный импорт одного файла → `SELECT SUM(amount)` не меняется.
- Импорт файла, теряющего часть контрагентов → импорт отменён, старый срез
  цел.
- Искусственная ошибка на середине вставки → в БД ноль строк за месяц (откат).

## Задача 2 — `cursor/sales-analytics-report`

**Заголовок:** `feat(sales): отчёт по номенклатуре — машиночитаемый вывод и тесты`

**Суть.** `analyzer.py` печатает отчёт в stdout текстом. Это неудобно:
результат нельзя сохранить в файл, сравнить с предыдущим прогоном или
отдать в другой инструмент.

**Что сделать:**

1. **Разделить вычисление и вывод.** Функция `analyze(db_path, month) -> dict`
   возвращает структуру:
   ```python
   {
     "month": "2026-11",
     "slice": {"source_file": ..., "period": ..., "rows": ..., "qty": ..., "amount": ...},
     "groups": [{"name": ..., "positions": ..., "models": ..., "qty": ...,
                 "amount": ..., "share_pct": ..., "avg_per_unit": ...}, ...],
     "cross_table": {"group": {"channel": amount}},
     "brands": [{"name": ..., "amount": ..., "share_pct": ...}, ...],
     "concentration": {"top1_pct": ..., "top3_pct": ..., ...},
     "returns": [...],
     "technical_rows": [...],
     "coverage": {"models": ..., "assigned": ..., "unassigned": [...], "sum_ok": true},
     "dynamics": [{"group": ..., "amount": ..., "per_day": ..., "delta_pct": ...}, ...],
   }
   ```
2. **Вывод — отдельный слой** с тремя форматами: `text` (человеческий),
   `json` (машиночитаемый), `csv` (плоская таблица позиций). Формат через
   `--format`.
3. **Не сломать текущий текстовый вывод** — он уже используется, текстовый
   формат должен остаться читаемым и содержать те же блоки.
4. **Покрыть тестами:** `analyze()` на фикстуре возвращает сумму групп, равную
   сумме среза; `coverage.sum_ok == True`; `unassigned` пуст; динамика
   нормирована на день (`per_day = amount / days`, а `days` считается через
   `split("-", 1)`).

**Критерии проверки:**

```bash
python -m pytest tests/test_sales_analyzer.py -q
python -m furniture_sales_database.sales_tools.analyzer --db furniture_sales_database/sales_tools/fixtures/sales_sample.db --month 2026-11 --format json
```

- JSON валиден, `coverage.sum_ok == true`.
- Сумма `groups[].amount` == `slice.amount` с точностью до копейки.
- В `dynamics` есть колонка `per_day` и `delta_pct` против прошлого месяца.

## Задача 3 — `cursor/sales-db-consistency`

**Заголовок:** `feat(sales): единая схема продаж — свести плоскую базу и нормализованную`

**Суть.** В проекте две несвязанные базы продаж:

- `sales.db` — плоская: `sales` (18 колонок, включая `buyer`, `salon`,
  `seller`, `buyer_type`, `report_filter`), `buyers`, `imports`. Это рабочая
  база, в ней свежие срезы и аналитика по номенклатуре.
- `furniture_sales_database/furniture_sales.db` — нормализованная:
  `products`, `sellers`, `platforms`, `suppliers`, `sales` с
  внешними ключами. Она богаче по справочникам (поставщики, платформы),
  но отстала по данным (последняя продажа — 07.10, тогда как в `sales.db`
  есть ноябрь), и её схема несовместима с плоской.

Из-за этого один и тот же вопрос («продажи диванов-кроватей в ноябре по
салонам») приходится решать двумя разными инструментами, и нельзя построить
сводку «реклама → продажи → салон».

**Что сделать:**

1. **Спроектировать целевую нормализованную схему**, которая покрывает оба
   случая без потери данных:
   - `products` — номенклатура (`sku`, `name`, `category`, `brand`);
   - `sellers` — продавцы (люди) с `buyer_type`/`channel_type`;
   - `channels` — точки продаж: салоны (`salon`) И платформы (`platform`),
     включая сайт;
   - `counterparties` — юрлица/ИП, которые покупают (б2б);
   - `sales` — продажа: `sale_date`, `period`, `product_id`, `seller_id`,
     `channel_id`, `counterparty_id`, `quantity`, `unit_price`,
     `total_amount`, `source_file`, `report_filter`, `is_return`;
   - справочник `suppliers` — сохранить из текущей нормализованной базы.
2. **Написать миграцию** `sales.db` → новая нормализованная схема:
   - `buyer`/`salon`/`seller` раскладываются по трём измерениям
     (`counterparty_id` / `channel_id` / `seller_id`);
   - `buyer_type='salon'` → салон становится `channels` с типом `salon`;
   - `buyer_type='ip'` → контрагент, а салон (если проставлен) — `channels`;
   - `parent_category` и `item_characteristic` сохраняются;
   - миграция **идемпотентна**: повторный прогон не создаёт дублей
     (`get_or_create` по имени/sku).
3. **Написать обратную проверку:** после миграции суммы по месяцам, по салонам
   и по контрагентам должны совпасть с исходной плоской базой до копейки.
   Расхождение — ошибка миграции, а не «округление».
4. **Миграция работает на фикстуре** `furniture_sales_database/sales_tools/fixtures/sales_sample.db` — в репо
   не попадают реальные данные.

**Критерии проверки:**

```bash
python -m pytest tests/test_sales_migration.py -q
```

- Суммы по всем месяцам совпадают с исходной БД (точное равенство float с
  допуском 0.01).
- Количество `products` равно числу уникальных `item_name` в исходнике.
- Повторный запуск миграции не меняет количество строк ни в одной таблице.
- Каждая продажа имеет не-NULL `channel_id` (салон/платформа) и
  `seller_id`.

## Порядок

Задачи независимы, но **задача 1 затрагивает `importer.py`, задача 2 —
`analyzer.py`, задача 3 — новую схему**. Если задачи будут выполняться
параллельно, конфликтов в файлах не возникнет: у каждой свой модуль и свой
тестовый файл. Задача 3 может опираться на пакет из задач 1 и 2, но не должна
править их файлы.
