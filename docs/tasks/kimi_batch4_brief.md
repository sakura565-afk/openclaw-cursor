## Задача 1 - `scripts/chain_texture_gate/`: гейт длинного клипа по НОВОЙ метрике

**Зачем.** Чейнинг (`scripts/h3_chain_pipeline_kimi/`) наконец починен - флаги
рендерера, звук со смещением и кроссфейдом, гейт по хвостовому дрейфу. Но его
**texture-гейт считает по энергии пор**, а мы уже знаем, что энергия не
отличает поры от зерна. Нужен гейт, который спрашивает «это вообще поры?»

**Что сделать.** Пакет `scripts/chain_texture_gate/`:

1. **Интегрируй `scripts/skin_texture_metrics/`** (пакет Kimi) в гейт: решение
   «текстура подходит» должно опираться на **survival ratio** добавленной
   компоненты и на структурный балл, а не только на энергию полосы.
2. **Порог-калибровка:** дай гейту два порога - минимальный survival (ниже
   него деталь шумовая, чанк не принимается) и минимальный структурный балл.
   Значения по умолчанию обоснуй числами из своего же измерения.
3. **Сравнение с базой:** гейт должен уметь сравнивать чанк не с абсолютным
   числом, а с **базовым чанком** (первый принятый чанк) - «текстура не хуже
   базовой». Это устойчивее, чем абсолютный порог.
4. **Отчёт и вердикт** по чанку: дрейф (средний и хвостовой), энергия пор,
   survival, структурный балл, принят/отклонён, причины.
5. **Сравнение с одиночным рендером.** Построй (офлайн, без GPU) таблицу:
   один чанк против собранного из нескольких, чтобы было видно, что
   chaining не ухудшает текстуру на стыках. Используй существующие артефакты
   из HERMES_SCRATCH_DIR (например `MASTURB2_V6.mp4`, `GOWN_P1.mp4`).
6. **Документация реального запуска** в README: команда длинного рендера с
   новым гейтом, но **не запускай** - GPU занят.

**Приёмка.** Модуль импортируется; тест доказывает, что BC-шум и «песок»
**отклоняются** гейтом, а реальная деталь проходит; `pytest -q` зелёный; нет
абсолютных путей; в README - почему survival, а не энергия.

## Задача 2 - `scripts/skin_metric_groundtruth/`: независимая правда для метрики

**Зачем.** Сейчас пороги метрики выбраны на том же материале, на котором
проверяются. Это не валидация. Нужен набор с **известным** ответом.

**Что сделать.** Пакет `scripts/skin_metric_groundtruth/`:

1. **Синтетическая правда с известным ответом.** Сгенерируй эталонные
   изображения, где структура пор известна конструктивно:
   - гладкая пластина без пор (класс «пластик»);
   - поле настоящих пороподобных ямок известного размера и плотности
     (класс «поры») - используй генератор из `scripts/pore_injector/`;
   - изотропный шум известной амплитуды (класс «шум»);
   - смесь: поры на гладкой коже + шум поверх.
   Метрика обязана разложить их по правильным классам.
2. **Слепой набор для глаза.** Собери листы (сетки) с файлами в
   перемешанном порядке и пронумерованными кропами - как это уже делает
   `scripts/eval_judge/` (MiniMax). Готовый промт для судьи приложи.
3. **Калибровочный отчёт:** построй таблицу «метка -> метрика -> класс» и
   покажи, где пороги метрики совпадают с глазной разметкой, а где нет.
   Если где-то не совпадают - напиши это прямо, это и есть результат.
4. **Рекомендованные пороги** с обоснованием и с оговоркой, что глаз остаётся
   за человеком.
5. **Сохранение отчётов** в JSON рядом с артефактами.

**Приёмка.** Набор сконструирован; метрика различает синтетическую праву
правильно; калибровочный отчёт создан; `pytest -q` зелёный; нет абсолютных
путей. В ответе честно скажи, где метрика **не** совпала с глазом.

## Задача 3 - `scripts/recipe_lint.py` + `scripts/recipes/`: линтер правила negative

**Зачем.** Три наших провала подряд шли из-за одного: negative не совпадал с
состоянием reference. Правило есть, но оно живёт только в голове и в
скилле-референсе. Сделай его машинным.

**Что сделать.**

1. **Линтер** `scripts/recipe_lint.py`: по промту, negative и описанию
   reference (текст) ищет **противоречия**:
   - negative требует «одето/закрыто», а промт или reference требует
     «голая/обнажённая/сдвинуто в сторону» (и наоборот);
   - negative запрещает «рука в белье», а промт требует её туда;
   - в negative есть «panties off», а промт говорит «fingers slide under the
     fabric»;
   - в negative есть «topless/nude», а reference - голая грудь;
   - в negative есть термины одежды, которых в reference нет.
   Вывод: список противоречий с конкретными терминами и **предложением
   правки**. Учитывай, что «nude» в negative означает «не полностью голая»
   и может конфликтовать с намерением оставить бельё.
2. **Рецептурный реестр** `scripts/recipes/` в JSON: все одобренные сцены с
   точными параметрами - чекпоинт, текстовый энкодер, стек LoRA с
   силами, разрешение, длина, steps, seed, промт, negative, разбор почему
   именно так. Начни с девяти одобренных клипов (серая постель, дамаск с
   вуалью, со сдвигом трусиков, грудь, накидка, платье) и добавь схему
   проверки, что имена LoRA ещё существуют в ComfyUI.
3. **CLI** `scripts/recipes/print_recipe.py --scene <id>` печатает готовую
   команду рендера; `--check-loras` сверяет имена с живым ComfyUI (если он
   доступен, иначе - честно «недоступно»).
4. **Тесты** на линтере: набор верных и неверных пар промт/negative с
   ожидаемым вердиктом.

**Приёмка.** Линтер ловит все перечисленные классы противоречий; реестр
содержит одобренные сцены; CLI печатает команду; `pytest -q` зелёный; нет
абсолютных путей.
